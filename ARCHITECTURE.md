## How a scan works

1. `POST /api/scan` receives `{ assetId, password }`.
2. The asset + its CIS template are loaded from the database.
3. `parseCisContent` validates the template against the `CisTest[]` shape —
   the app's **one and only** schema validation point. A bad template ends the
   stream with `stage: "invalid_template"` and no SSH connection.
4. The scanner connects over SSH (configurable timeouts/keepalive/source
   interface — see [Configuration](#configuration-environment)) and runs the
   privilege preflight.
5. Each automated rule's commands run in order; the captured stdout is judged
   by the rule's `check`. A `test_result` event is emitted per rule.
6. On success the full snapshot is persisted via `recordScan` and a
   `complete` event is emitted. A failed connection attempt writes **no**
   `ScanHistory` row (it is not a scan result).

### Streaming protocol
The scan runs through `POST /api/scan`, which streams progress to the browser
as **one JSON event per line** over a single HTTP response. The client reads it
incrementally with `response.body.getReader()` — no WebSockets, no polling.

Event shapes (`src/lib/types.ts` → `ScanEvent`):

- `status` — `preparing` → `testing_connectivity` → `connected` →
  `verifying_privileges` → `scanning_started` (carries `total` rules).
- `test_result` — one per rule (`passed` / `failed` / `error`), always the
  same payload shape regardless of status.
- `error` — `invalid_template` / `connection_failed` / `privilege_failed` /
  `scan_failed`; the stream ends immediately.
- `complete` — final score + counts.

### Privilege model
- If the asset username is `root`, audit commands run directly.
- Otherwise every complete audit command is wrapped as
  `sudo -S -p '' -- /bin/sh -c '<command>'` with the password supplied over
  SSH stdin (`-S`), so pipes, redirects, and chains are all elevated — not
  just the first word.
- A preflight (`id -u`, or `sudo -S -k -p '' -- id -u` for non-root) runs
  after connect and before any rule. A failed preflight aborts the scan with
  `stage: "privilege_failed"` rather than producing garbage results.

### Structured check evaluation
Each rule's `check` is one of six typed variants (`src/lib/types.ts` →
`CheckType`), evaluated mechanically:

- `output_empty` — pass if stdout is empty.
- `output_contains` — pass if stdout includes a substring.
- `output_equals` — pass if trimmed stdout equals a value.
- `output_matches_regex` — pass if a regex matches stdout.
- `numeric_gte` — pass if a number extracted from stdout ≥ a value.
- `manual` — not automatable; never executed by the scanner and excluded from
  the score (keeps the score's meaning consistent: every counted rule was
  mechanically checked).

Rule results are `passed`, `failed`, or `error`. An execution problem (sudo
failure, permission denied, command not found, timeout, SSH channel error) is
**never** reported as a confirmed compliance failure; errors get their own
summary section and a broad failure class
(`ScanErrorCategory`: `timeout` / `execution` / `channel`).

## Compliance report (PDF)

Reports are served by `GET /api/reports/[scanId]` (`src/app/api/reports/[scanId]/route.ts`)
— a Route Handler (not a Server Action) because the response is a binary PDF
download. The `scanId` is the **only** client input; the authoritative report
data (asset, counts, per-rule snapshot) is loaded server-side from the
`ScanHistory` row written at scan time, so browser-side tampering cannot alter
a report.

The report is generated by `src/lib/report.ts` with PDFKit primitives (text,
rects, vector arcs). Template values (descriptions, remediation, evidence) are
always treated as plain text, and command text is reproduced verbatim,
including shell characters like `$` and `|`.

### Report structure

1. **Header** — report identity + asset information + scan summary.
2. **Doughnut chart** — green/red/amber segments with the score in the middle.
3. **Failed rules** — one section per finding: audit procedure, original
   commands, sanitized evidence, remediation in a distinct box.
4. **"Rules That Could Not Be Evaluated"** — execution errors, separate from
   findings, with the sanitized reason and a compliance-state note (CIS
   remediation is deliberately NOT shown for these).
5. **Passed-rules appendix** — compact rows, wrapping columns, table header
   repeated on every page the table continues onto.

### Layout invariants

- `bufferPages: true` so the footer pass can revisit every page.
- Content boxes are **page-aware**: anything taller than the remaining space
  breaks across pages into one boxed portion per page — never one oversized
  rectangle that gets clipped.
- Box fill and border are drawn with `fillAndStroke()`; `fill()` consumes the
  path, so a follow-up `stroke()` would not reliably draw borders.
- A label is never orphaned at a page bottom: label + caption + a first
  meaningful box portion are reserved together.

### Doughnut chart

The chart draws colored pie slices (passed = green, failed = red, errors =
amber) and overlays a single white center circle to form the doughnut hole,
with the score (`54%`) centered above the `SCORE` label.

Each segment uses **exactly one `arc()` call** followed by a line to the center
and a `closePath()` — it never constructs an annular segment with an outer arc
plus a reverse inner arc. PDFKit's `arc()` starts its own subpath, so a second
reverse inner `arc()` would create open subpaths that PDF viewers close with
diagonal chords — the triangular artifacts seen in earlier builds.

Special cases keep the chart correct in every state:

- **100% one category** — a filled outer circle + inner white circle.
- **Zero total** — an empty ring drawn at the midpoint radius
  `(R_OUTER + R_INNER) / 2` with the ring width as the line width, so it keeps
  the same outer=70 / inner=44 dimensions as a real chart.
- **Empty/100% use no `arc()` at all** — only `circle()`, which cannot produce
  the artifact.

The legend shows both raw counts and percentages (e.g.
`Passed — 54 (54%)`), computed by the `percentage()` helper.

## Data model

PostgreSQL via Prisma (`prisma/schema.prisma`); ids are `uuid(7)` (time-ordered
to avoid random-index bloat).

- **CisTemplate** — `id`, `name`, `content` (JSON array of `CisTest`),
  `createdAt`.
- **Asset** — `id`, `title`, `ipAddress`, `username` (SSH account, default
  `user`), `cisId` (→ CisTemplate), `createdAt`.
- **ScanHistory** — `id`, `assetId` (→ Asset, cascade delete), `score`
  (0–100), `passed`/`failed`/`errors`/`total` counts, `results` (JSON
  `StoredRuleResult[]` — the authoritative per-rule snapshot), `scannedAt`.

The `ScanHistory.results` snapshot is the server's own trusted record of which
rules passed/failed/errored during that scan — including the audit commands,
procedure, remediation text as it existed at scan time, and sanitized
per-command evidence. The browser never supplies report data; reports are
generated from this snapshot by `scanId`.

## Security model

- The SSH password is memory-only and never persisted, logged, or sent in any
  streamed event.
- No command stdout/stderr is streamed to the browser; only short, sanitized,
  length-bounded diagnostics accompany `error` results.
- `redactSecret` guarantees the password can never leak into a streamed
  diagnostic or error message; `truncateText` bounds the size of any streamed
  diagnostic; `sanitizeDiagnostic` combines both for every `error` message
  that leaves the server.
- Evidence destined for reports is run through `prepareReportEvidence`, which
  strips ANSI escapes, strips control chars (preserving tabs/newlines), redacts
  the secret, and hard-caps the length (`MAX_EVIDENCE_LENGTH = 16_000`).
- Reports are generated **only** from the server-persisted scan snapshot,
  keyed by `scanId`; the browser cannot supply report data.
- Template validation happens before any network I/O, so malformed input never
  reaches the target host.
- Run only on localhost or behind HTTPS: the root password crosses the network
  on every scan request.

## Configuration (environment)

SSH/scan tuning lives in `src/lib/scan-config.ts` and is read from optional
environment variables with safe defaults:

| Env var | Default | Purpose |
| --- | --- | --- |
| `SCAN_SSH_DEFAULT_PORT` | `22` | SSH port when the asset IP has none |
| `SCAN_SSH_READY_TIMEOUT_MS` | `10000` | ssh2 `readyTimeout` (handshake) |
| `SCAN_SSH_SOCKET_TIMEOUT_MS` | unset | ssh2 socket `timeout` |
| `SCAN_SSH_KEEPALIVE_INTERVAL_MS` | unset | ssh2 keepalive interval |
| `SCAN_SSH_LOCAL_ADDRESS` | unset | source IP/interface to bind |
| `SCAN_SSH_LOCAL_PORT` | unset | source port to bind |
| `SCAN_COMMAND_TIMEOUT_MS` | `60000` | per audit-command timeout (Promise race) |

The SSH username is **not** part of this config — it is stored per-asset in
`Asset.username` and is the single source of truth for who the scanner connects
as. `SCAN_COMMAND_TIMEOUT_MS` is implemented in the scanner with a Promise
race (the only reliable way to bound a hung audit command, since `ssh2`'s
`ExecOptions` exposes no per-command timeout).

## Tests

Unit tests run with `tsx --test` under the React Server conditions
(`--conditions=react-server`) so the `server-only` imports resolve:

```bash
npm test
```

Test files:

- `src/lib/shell-quote.test.ts` — POSIX quoting, including round-trips through
  a real `/bin/sh` (simple strings, mixed quotes, `$` expansion NOT performed,
  backticks/redirects/semicolons/globs/newlines, and strings that are only
  single quotes).
- `src/lib/sanitize.test.ts` — secret redaction, truncation, ANSI/control
  stripping, and `prepareReportEvidence` (secret redaction, control-char
  removal, large-output truncation, short-clean-output passthrough).
- `src/lib/report.test.ts` — PDF generation (`%PDF-` header, valid buffer),
  text extraction from Flate-compressed PDF streams (decoding pdfkit's
  WinAnsi-hex `TJ` arrays), legend percentages (`Passed — 82 (82%)`), an
  all-error report that does not masquerade as a clean pass, NaN/non-finite
  score rejection, long-name safe filenames, and a mixed-result doughnut
  regression case (`54/34/12`) that guards against the diagonal triangular
  artifacts caused by constructing annular segments with two `arc()` calls.
